Subagents & Automation

What are subagents in Claude Code? (And how to make your own)

A subagent is a helper that Claude Code sends off to do one side task in its own separate workspace. It does the messy work out of sight and brings back only a short summary, so your main conversation stays clean.

AgentDrills team · Updated November 23, 2026 · 8 min read

That's the whole idea in one sentence. Claude Code can hand a job, like searching through a project or running tests, to a helper. The helper reads files, runs commands and digs through results on its own. When it's done, you only see what it found. You can use the helpers Claude Code comes with, and you can make your own with a single request.

This guide explains what that means in plain words, when it's worth it, and how to set up and call your first subagent. If a word is new, don't worry. Each one is explained the first time it shows up.

The short answer: a helper with its own desk

When you work with Claude Code, everything happens in one conversation: your messages, Claude's replies, and every file and command result Claude looks at along the way. All of that sits in Claude's context, which is its working memory for the session.

Think of context as a desk. Every file Claude reads is another sheet of paper on it. A subagent gets its own desk. It starts empty, does its task there, and walks back to your desk with one note: the answer. The pile of paper it needed stays on its desk.

Each subagent also has its own instructions, its own list of tools it's allowed to use, and its own permissions (rules for what it may do without asking you). A tool is simply an action Claude can take, like reading a file, searching, or running a command in the terminal (the text window where you type commands).

Why your main conversation gets crowded

Say you're working on a small to-do app in a folder called my-project and you ask Claude where the to-dos get saved. To answer, Claude may open five files and run a search. Every one of those results lands in your conversation, even though you'll never look at most of them again.

Do that a few times and the desk fills up. You can see how full it is with a slash command (a command for Claude Code itself, starting with /):

> /context

A crowded context isn't just untidy. The more there is, the more Claude has to sift through, and the easier it is for the important details to get lost. Subagents are one of the best ways to keep that from happening, because the noisy part of the work never reaches your desk.

Good to know: a subagent still does real work. Its requests count toward the same usage limits as your main conversation (the amount of Claude your plan lets you use in a given period). You save space in your conversation, not usage.

Claude already uses built-in subagents

You don't have to set anything up to see a subagent in action. Claude Code comes with a few built in, and it uses them on its own when a task fits:

  • Explore is a fast helper for searching and understanding code. It can only read, never change files.
  • Plan gathers information while you're in plan mode (a mode where Claude researches and suggests a plan but changes nothing), so Claude can show you a plan before it changes anything.
  • general-purpose handles bigger tasks with several steps that need both looking around and taking action.

You can also simply ask for one. In the to-do app, you might type:

> use a subagent to find where todos are saved and loaded

In the terminal, the hand-off shows up as one line with the helper's name and a short description of its task, followed by Claude's answer:

⏺ Explore(Find where todos are saved and loaded)

⏺ Todos are saved and loaded in one place:
  - src/storage.js – loadTodos() and saveTodos(todos) use localStorage
  - src/app.js – calls loadTodos() on start and saveTodos() after every change

Notice what you didn't get: a long list of every file the helper opened. That's the point.

When a subagent helps, and when it doesn't

A subagent shines when a side task produces lots of output that you won't read again. Some typical examples:

  • Searching a project to find where something happens
  • Running the tests and reporting only what failed
  • Reading through long logs (records a program writes while it runs) to find one error
  • Doing the same kind of job again and again with the same instructions

It's less useful for small, quick things. If you want a typo fixed in one line, just ask. Handing it to a helper only adds a step. A good rule of thumb: lots of output you won't read → subagent. Small and obvious → just ask.

One more thing to remember: a subagent starts with a fresh, empty desk. It doesn't see what you and Claude talked about earlier. Claude passes it the task, so the clearer your request is, the better the helper's result will be.

Make your own: just ask Claude

The built-in helpers are general. Your own subagent can be a specialist, like a tester or a reviewer, with exactly the rules you want. The easiest way to make one is to describe it to Claude in plain English:

> create a project subagent called test-runner that runs the tests and reports failures

Claude writes a small file for you and, as usual, asks before it saves anything. You review it and approve it, the same way you approve any other change.

What about /agents? In older versions of Claude Code, the /agents command opened a menu for creating subagents. In current versions it just reminds you to ask Claude or edit the files yourself. Asking Claude is the simplest route either way.

Claude Code notices a new or changed subagent file within a few seconds, so you don't need to restart. If a new subagent doesn't show up, restarting Claude Code fixes it.

What's inside a subagent file

A subagent is just a text file written in Markdown, a simple format for plain text with a little formatting. Here's what the test-runner file looks like:

---
name: test-runner
description: Runs the test suite and reports failures. Use after code changes.
tools: Bash, Read, Grep
---
Run npm test. Report which tests fail and why. Never edit files.

The part between the two --- lines holds the settings. Below it are the helper's instructions, written like a note to a colleague. The settings that matter most:

  • name: what you call the helper. Required.
  • description: when Claude should use it. Required, and important, because Claude reads it to decide when to hand over a task on its own.
  • tools: which actions the helper may use. Optional. Leave it out and the helper gets the same tools as Claude.

Limiting the tools is a simple safety trick. The test-runner above gets Bash (run commands), Read and Grep (search), but not the tools for editing files. So it can run your tests, but it can't change your code, even by mistake.

Tip: you can also pick which model a subagent uses with a model line, for example a faster, cheaper one for simple jobs. That's optional. Leave it out until you need it.

Calling a subagent by name

Once your helper exists, there are a few ways to use it. Claude may pick it on its own when a task matches the description. To be sure it's used, call it yourself. You can type @agent- followed by its name:

> @agent-test-runner run the tests

Typing @ also opens a list of suggestions, where your subagents show up next to your files. Or you can just say it in plain English:

> use the test-runner subagent to check my last change

Either way, you'll see the hand-off line and then the result:

⏺ test-runner(Run the test suite)

⏺ test-runner reports: all 12 tests pass. No failures.

The full test output stayed with the helper. You got the one line you needed.

Project or personal?

Where you save a subagent decides where you can use it:

  • .claude/agents/ inside your project folder: the helper belongs to that project. If you share the project with others, they get the same helper. This is a good home for helpers tied to one codebase, like the test-runner.
  • ~/.claude/agents/ in your home folder (the ~ is a shortcut for it): the helper is personal and works in all your projects. Good for general helpers, like a code reviewer you always want around.

If both places have a helper with the same name, the one in the project wins. When you ask Claude to create a subagent, just say "project" or "personal", and it'll save the file in the right place.

Try it yourself

Subagents sound advanced, but the habit is simple: let a helper carry the noisy side tasks, and keep your own conversation for the work you care about. Start with the built-in Explore helper, then make one specialist you'll actually use, like a test-runner.
