Point Claude at the right files with @ and run commands with !

Claude Code can find things on its own, but when you already know where to look, telling it directly is faster, cheaper and more accurate.

AgentDrills team · Updated November 23, 2026 · 5 min read

When you ask Claude Code a question, it often starts by searching: it lists files, greps for keywords and reads a few candidates before answering. That's great when you don't know where something lives. But often you do know. You're looking at src/utils.js in your editor right now. Making Claude search for it wastes time and context, and occasionally leads it to the wrong file.

Two small prefixes fix this: @ for files and ! for shell commands.

@ mentions: hand Claude a file directly

Type @ anywhere in your message, and Claude Code shows a list of files in your project. Keep typing to filter, press Tab to complete. The file is attached to your message, so Claude can work with it immediately, without a separate search step.

> explain @src/utils.js

Paths are relative to the folder you started Claude in. So it's @src/utils.js, not @utils.js and not the full path from your home folder. The autocomplete takes care of this if you let it.

Mention several files at once

The real power shows when you combine files. Comparing two files is a classic task that's awkward to describe in words but trivial with mentions:

> which functions in @src/utils.js are missing tests in @tests/utils.test.js?

A few more patterns that work well:

  • Follow an example: add a settings page that works like @src/pages/profile.js
  • Respect a spec: implement the API described in @docs/api.md
  • Debug with evidence: this error comes from @src/storage.js, here's the stack trace: …
  • Whole folders: mentioning a directory gives Claude an overview of what's inside, which is useful for "where should this new file go?"

Why it gives better answers

Claude only knows what is in its context. When it searches by itself, it decides what's relevant, and it can miss things or read the wrong version of something. When you mention files, you decide what's relevant. You also save context space by not filling it with search results, which keeps long sessions sharper. More on that in the guide on context.

Rule of thumb: if you could point at the file on your screen, mention it with @. If you don't know where the code lives, describe it and let Claude search.

! bash mode: run a command without leaving Claude

Sometimes you just want to run a quick command yourself: check git status, list a folder, run one test. Switching to another terminal window breaks your flow. Instead, start your input with !:

> !git status

The command runs directly in your shell, exactly as if you'd typed it in a terminal, and the output appears in the session. Two things make this more useful than it sounds:

  1. Claude sees the output too. Run !npm test, see three failures, then simply type "fix those". Claude already has the test output in front of it.
  2. No approval needed. You typed the command yourself, so there's no permission menu. It's your command, not Claude's.

That second point is also the one caveat: Claude can't protect you from your own commands. Bash mode runs exactly what you type.

Good uses of bash mode

  • !git status or !git diff to see what Claude changed
  • !ls src to remind yourself of the structure
  • !npm test to show Claude the current failures
  • !cat .env.example to share a config template (never real secrets)

A worked example: fixing a bug with @ and !

Here's how the two prefixes work together in a real debugging session. Say a user reports that overdue todos aren't highlighted. You suspect the date helper.

  1. Reproduce it. !npm test -- utils runs only the utility tests. One fails: isOverdue returns false for yesterday's date.
  2. Point at the cause. the failing test is about @src/utils.js, why does isOverdue return false for yesterday? Claude already sees the test output from step 1 and the exact file you mentioned, so it can go straight to the function instead of hunting around.
  3. Approve the fix. Claude spots that the comparison uses local time on one side and UTC on the other, and proposes a one-line change. You read the diff and approve it.
  4. Verify. !npm test -- utils again. All green.

Four short inputs, no window switching, and Claude never had to guess which file you meant. Compare that to "overdue todos aren't highlighted, can you fix it?", which works too, but usually after several rounds of searching and reading.

Pitfalls to avoid

  • Mentioning everything. Attaching ten large files "just in case" fills up Claude's context and buries the relevant part. Mention what matters for the question.
  • Huge generated files. Don't mention build output, lock files or minified bundles. They're long and rarely useful.
  • Secrets. Never @-mention or !cat a file with real passwords or API keys. Everything you share goes into the conversation.

!Run a shell command yourself!git status

Mixing them up is a common beginner slip: /git status isn't a command, and src/utils.js without the @ is just text, which Claude may or may not decide to open. Once these three prefixes are in your fingers, sessions get noticeably faster and more precise.

Claude Code is updated often, and the exact behaviour of autocomplete may differ slightly between versions.
