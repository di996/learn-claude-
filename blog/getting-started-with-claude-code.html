Getting started with Claude Code: your first session

Claude Code is easy to install and surprisingly easy to misuse. Here is how to start your first session the right way, and what is actually happening on screen.

AgentDrills team · Updated November 23, 2026 · 6 min read

Claude Code is an AI coding assistant that lives in your terminal. You type what you want in plain English, and it reads your files, suggests changes, runs commands and explains what it did. If you have only used chat-style AI tools before, the biggest change is this: Claude Code works directly on your project. It doesn't just answer questions about code you paste in. It goes and looks.

That makes the first few minutes important. Start it in the wrong place, or ask in the wrong way, and you'll get vague answers. Start it right, and it feels like pairing with a colleague who has already read the whole codebase.

Step 1: Start in the right folder

Claude Code works on the files in the folder you launch it from. That folder is its whole world for the session. So before anything else, move into the root of the project you want help with:

cd my-project
claude

The "root" is usually the folder that contains files like package.json, README.md or your .git folder. If you start Claude in your home folder instead, it either can't find your code or has to guess which of your hundreds of folders you mean.

Tip: If you work on several projects, open one terminal tab per project and start a separate Claude session in each. Sessions don't share context, which is exactly what you want.

Step 2: Get to know the screen

When Claude Code starts, you'll see a short welcome box with your current folder (cwd), followed by an input box with a > prompt. That box is where you talk to Claude. A few things are good to know right away:

  • Plain text is a message to Claude. Just type a question or a task and press Enter.
  • Text starting with / is a command for Claude Code itself, like /help or /exit. Typing / shows a list you can pick from.
  • The line under the input box shows the current mode. You'll learn about modes later; for now, the default is fine.

Step 3: Ask a question before you ask for a change

The best first message isn't a task. It's a question. Ask Claude what the project does:

> what does this project do?

This does two things. You get a quick overview, and you get to see how Claude explores a codebase. You'll notice it doesn't answer immediately. First, a few lines appear that start with ⏺:

⏺ Read(README.md)
  ⎿  Read 24 lines
⏺ Read(package.json)
  ⎿  Read 19 lines
⏺ Read(src/app.js)
  ⎿  Read 88 lines

Each of these is a tool call: an action Claude decided to take on its own to answer your question. Read opens a file, Search looks for text across many files, Bash runs a terminal command, and Update or Write changes files. The indented line under each one (after ⎿) shows the result.

Reading tool calls is a habit worth building from day one. They tell you what Claude actually based its answer on. If it answers a question about your database without ever reading the database code, that's a red flag.

Step 4: Follow up like you would with a colleague

Claude remembers everything in the current session, so you don't need to repeat yourself. Follow-up questions are short:

> which file handles saving the todos?

Here Claude will typically use Search to find the relevant code instead of guessing. Good follow-ups are specific. Compare:

VagueSpecific
how does it work?how does a todo get saved after I tick it?
is the code good?are there any functions in src/utils.js without tests?
fix itthe date shows as "Invalid Date" on Safari, can you find out why?

The specific versions give Claude something to search for, and they give you an answer you can check.

Step 5: Exit cleanly

When you're done, type /exit. Pressing Ctrl+C twice also works. A very common beginner mistake is typing exit without the slash. Inside Claude Code that's just a message, so Claude will politely try to answer it.

Exiting doesn't lose your work. Any files Claude changed stay changed, and the conversation is saved, so you can come back to it later with claude --continue.

What Claude can and can't see

It helps to have a clear picture of what Claude Code actually has access to, because it explains a lot of its behaviour.

  • It can see files in your project folder and everything below it. It reads them on demand, when it decides a file is relevant, not all at once.
  • It can't see your screen or your editor. If you have a file open in VS Code, Claude doesn't know that unless you tell it. Saying "the file I have open" means nothing to it; name the file instead.
  • It doesn't know what happened before this session, unless you continue an earlier conversation or it's written in a CLAUDE.md file. More on that in the guide on slash commands.
  • It can run commands, but only with your permission. Reading is free; editing files and running shell commands require approval by default.

This is also why good questions name things: files, functions, error messages, the exact behaviour you see. Claude is very good at following a trail. Give it the start of the trail and it'll find the rest.

Finally, remember that Claude can be wrong. It is usually right about what code does, because it can read it, but it can be overconfident about things it can't check, like how your production server is configured. When an answer matters, ask Claude to show you where in the code it found it.

Common first-day mistakes

  • Starting in the wrong folder. Always cd into the project first.
  • Asking for a big change before understanding the code. A question or two first helps both you and Claude.
  • Ignoring the tool calls. They are your best clue to whether an answer is grounded in your actual code.
  • Typing commands without the slash. exit, help and clear all need a / in front.
  • Treating it like a search engine. Claude Code shines when you give it a real task in a real project, not trivia questions.

What to learn next

Once you're comfortable asking questions, the next step is letting Claude change things. That means understanding permissions: when Claude asks before editing a file, what the options mean, and when it's safe to let it work without asking. That's the subject of the next guide.
