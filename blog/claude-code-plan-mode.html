Plan mode and auto-accept: choosing how much control to give

One shortcut, Shift+Tab, decides whether Claude asks before every edit, edits freely, or only thinks and plans. Picking the right mode is half the skill.

AgentDrills team · Updated November 23, 2026 · 6 min read

If you've worked through a few tasks with Claude Code, you know the rhythm: Claude proposes an edit, you approve it, repeat. For small changes that's perfect. For a feature that touches eight files, approving each edit one by one gets tedious, and approving them blindly defeats the purpose. Modes solve this by letting you choose, per task, how much control you want.

The three modes

Press Shift+Tab while in Claude Code to cycle through them. The line under the input box tells you which one is active:

ModeIndicatorWhat Claude may do
Normal(nothing shown)Read freely; asks before each edit and command.
Accept edits⏵⏵ accept edits onEdits files without asking; still asks before shell commands.
Plan mode⏸ plan mode onReads and researches, but makes no changes at all until you approve a plan.

The cycle wraps around, so if you overshoot, keep pressing until you're back where you want to be.

Accept edits: speed when you trust the direction

Accept-edits mode is the "I've seen enough, go ahead" setting. Claude writes code without stopping for approval, which makes multi-file changes dramatically faster. Commands still need your OK, so it can't, for example, delete a folder or push to GitHub on its own.

Use it when:

  • the task is well understood and you've already seen Claude's approach
  • you're working in a git repository, so every change can be reviewed and undone afterwards
  • the change is mechanical: renaming, moving code, adding types, updating tests
Review at the end. Auto-accept doesn't mean "don't look". It means "look once, at the end". Run !git diff or open your editor's source-control view when Claude is done.

Plan mode: think before typing

Plan mode is the opposite. Claude can read, search and reason about your code, but it won't change a single file. Instead, it presents a plan and asks whether to go ahead. This is the most underused feature among beginners, and one of the most valuable.

Try it with a feature that touches several parts of the app:

> add due dates to todos

In plan mode, Claude reads the relevant files and comes back with something like:

Here's my plan:
1. Add an optional `due` field to each todo in storage.js
2. Add a date picker next to the "Add" input in index.html
3. Show the date with formatDate() and highlight overdue items
4. Add tests for isOverdue() in tests/utils.test.js

Then it asks how you want to proceed: go ahead with edits auto-accepted, go ahead but approve edits manually, or keep planning. "Keep planning" is not a dead end. It's your chance to say "skip the tests for now" or "use the native date input, no library", before a single line of code is written.

Why planning first saves time

  • Mistakes are cheaper in a plan than in code. Rejecting step 2 of a plan takes a sentence. Undoing step 2 after it's been implemented across four files takes much longer.
  • You learn the codebase. A plan shows you which files matter for a feature, which is useful even if you end up changing the approach.
  • Claude does better work. Researching before writing leads to changes that fit the existing code instead of fighting it.

How to judge a plan

A plan is only useful if you actually read it critically. You don't need to be an expert to do that. Look for these signs.

Signs of a good plan

  • It names real files from your project, and they're the ones you'd expect.
  • It reuses what exists. "Use the existing formatDate()" is a great sign. Claude has read the code and is building on it.
  • It's in small, ordered steps, each of which you could check on its own.
  • It mentions tests or how to verify the change.

Red flags

  • New libraries you didn't ask for. Ask whether it can be done without them.
  • Rewriting things that work. "Refactor the storage layer" as step one of adding a date field is scope creep.
  • Vague steps like "update the UI" or "handle edge cases". Ask what exactly that means.
  • It touches areas you consider off limits, like authentication or payment code, when the task didn't require it.

When you spot a red flag, stay in plan mode and say so in plain words: "don't add a library, use the browser's built-in date input" or "leave the storage layer alone". Claude revises the plan. Two or three rounds of this are completely normal and still much faster than fixing code afterwards.

Which mode for which task?

TaskGood mode
Fix a typo or tweak one lineNormal: just ask and approve
A new feature across several filesPlan mode first, then accept edits
You don't fully understand the problem yetPlan mode, and keep planning until you do
Mechanical refactor you've already scopedAccept edits
Anything touching payments, auth or production dataNormal, and read every diff

A workflow that works

  1. Press Shift+Tab into plan mode and describe the task.
  2. Read the plan. Push back on anything that's too big, too clever or missing.
  3. Approve it with auto-accepted edits once it looks right.
  4. Let Claude work, and keep an eye on the tool calls as they scroll by.
  5. Review the full diff at the end, then run the tests.

This combines the best of both worlds: you make the important decisions up front, and Claude does the typing without interrupting you twenty times.

Claude Code is updated often, and the names and order of modes may change slightly between versions. The indicator under the input box always tells you which mode you're in.
