Permissions & Safety

Claude Code permissions: when to say yes, and when to say no

Claude Code asks before it touches your files or runs a command. Those little menus are your steering wheel. Here's how to read them and when each answer makes sense.

AgentDrills team · Updated November 23, 2026 · 6 min read

The moment you ask Claude Code to change something rather than explain it, you'll meet the permission system. By default, Claude can read files freely, but it stops and asks before it edits a file or runs a shell command. This is the core safety mechanism in Claude Code, and once you understand it, it's also the core of a fast workflow.

The basic loop: ask, review, decide

Say you ask for a feature:

> add a button that clears completed todos

Claude reads the relevant code, explains its plan in a sentence, and then shows you an edit approval. It looks roughly like this:

Edit file
  src/app.js
  + function clearCompleted() {
  +   todos = todos.filter(t => !t.done);
  +   saveTodos(todos);
  +   render();
  + }

Do you want to make this edit to app.js?
❯ 1. Yes
  2. Yes, allow all edits during this session (shift+tab)
  3. No, and tell Claude what to do differently (esc)

The lines starting with + will be added, lines starting with - removed. This is called a diff. Reading diffs is the single most valuable skill when working with any AI coding tool. You don't have to understand every character, but you should understand roughly what changes and where.

What each option actually means

OptionWhat happensUse it when
1. YesThis one edit is applied. Claude asks again next time.You want to review each change, especially early in a task.
2. Yes, allow all editsThis edit is applied, and Claude may edit files without asking for the rest of the session.You trust the direction and don't want to approve twenty small edits.
3. NoNothing is changed. Claude stops and waits for you to explain what you want instead.The change is wrong, too big or not what you meant.

You can pick options with the arrow keys and Enter, or press the number. Esc is a shortcut for "No".

Good to know: option 2 covers file edits. Shell commands still have their own approvals, which is a sensible split: editing a file is easy to undo, running a command might not be.

Command approvals

When Claude wants to run something in your terminal, like your test suite, it shows a similar menu:

Bash command
  npm test
  Run the test suite

Do you want to proceed?
❯ 1. Yes
  2. Yes, and don't ask again for npm test commands in /Users/you/my-project
  3. No, and tell Claude what to do differently (esc)

The middle option creates a permission rule: Claude remembers that this kind of command is fine in this project and won't ask again. That's perfect for safe, repetitive commands like running tests, linting or type-checking. It is a terrible idea for anything destructive.

Commands worth allowing

  • Running tests: npm test, pytest
  • Linters and formatters: npm run lint, prettier
  • Read-only git commands: git status, git diff, git log

Commands to approve one at a time (or reject)

  • Anything that deletes: rm, rm -rf
  • Anything that publishes or deploys: git push, npm publish
  • Anything that touches production data or costs money
  • Installing packages you didn't ask for

Saying no is a feature, not a failure

Beginners often feel they have to say yes to keep things moving. The opposite is true. Rejecting a bad step is how you steer. When you pick "No", Claude doesn't give up; it waits for direction. So reject, then say what you actually want:

> keep the tests, just skip the slow one

Claude adjusts and tries again. This ask → review → approve-or-redirect loop is the heart of working with Claude Code. Most good sessions involve a few "No"s.

Managing your rules later

Every "don't ask again" you choose is stored as a rule. If you later want to review or remove them, use the /permissions command inside Claude Code. Rules can also be written into the project's settings file, so a whole team shares the same list of safe commands. That's a topic for later; for now it's enough to know that nothing you allow is permanent or hidden.

When you approved something you shouldn't have

It happens to everyone: you approve an edit a bit too quickly and then realize it broke something. The good news is that file edits are easy to undo, as long as your project uses git.

  • Ask Claude to revert it. "Undo the last change to src/app.js" works well, because Claude remembers exactly what it changed in this session.
  • Use git yourself. git diff shows every change since your last commit, and git restore src/app.js throws away the changes to one file.
  • Commit before big tasks. A quick commit before you ask for a large change gives you a clean point to return to. Many people ask Claude to do this for them: "commit the current state before we start".

Commands are a different story. A deleted folder or a published package can't always be taken back, which is exactly why command approvals are separate and why you should read them carefully. If you're working in a folder that isn't under git yet, run git init and make a first commit before you let Claude make serious changes. It's the cheapest insurance there is.

Tip: If you're unsure what a command does, choose "No" and ask: "what would that command do, and is it safe?" Claude will explain before you decide.

A sensible default workflow

  1. Start a task with per-edit approvals (option 1) until you've seen that Claude understood the task.
  2. Allow safe commands permanently the first time they come up, so tests run freely.
  3. Switch to allowing all edits once the direction is clear, and review the result at the end with git diff.
  4. Never auto-approve destructive commands. The few seconds it takes to read them are always worth it.

This keeps you in control where it matters and out of the way where it doesn't. In the plan mode guide you'll see a third way: letting Claude make a plan first and approving the whole plan at once.

Claude Code is updated often, and the exact wording of menus may differ slightly from what's shown here.
